# AutoPPT 邀请制网页版：技术部署交付

第一版发布范围：邀请注册、账号独立工作区、个人风格与试做、逐字稿拆页与图片制作、修改与历史、普通放映、图片/PPTX/Markdown/项目包导出、管理员邀请码与额度管理。首批建议邀请 10 人；新账号默认 20 张图片额度、全站模型并发 2，可配置。既有账号余额不会因调整注册额度被改写。

图片制作默认先试一页，再确认其余页面。制作台支持当前范围的标题/讲稿/上屏文字/原页码搜索，每组最多展示 24 页；浏览分组不改变页序或完整导出。继续生成与补图的确认窗口会检查账号可用额度，不足时明确提供按页序分批生成，零额度不会从这些入口提交新图片任务。额度提示不替代服务器逐张预留，也不承诺锁住整个批次额度。

数字人、AI 口播生成、声音复刻和动态演示制作暂不开放；Mac App 继续独立使用。本次部署不涉及卸载 App、同步本机项目或上传本机工作区。

## 一、交付物与准备资料

部署包是可复现的**源码部署 ZIP**，不是 Mac 安装包，也不包含预先下载的 Docker 镜像。解压后的 `AutoPPT-Web/` 包含源码、Docker/HTTPS 配置、部署检查工具、备份恢复工具、说明与 `RELEASE.json`。服务器需能拉取 Docker 基础镜像和 npm 依赖。

ZIP 旁的 `.sha256` 校验包完整性；包内 `RELEASE.json` 记录准确提交号和源码文件校验。`deploy/release.env.example` 已写入对应提交号和构建时间；每个部署目录都应保存原 ZIP、校验文件和发布记录。

请技术同事准备以下资料，直接填到服务器文件中；无需把 Key 或密码发回聊天：

| 资料 | 填写位置与要求 |
| --- | --- |
| Linux 服务器 | 建议先以 4 核/8 GB/100 GB SSD 做小规模试点，这是容量起点，需观察实际负载。安装 Docker Engine 和 Compose 插件；模型调用需能出站访问供应商 |
| 域名/DNS | 域名 A 记录指向服务器；已有 AAAA 记录时需确认 IPv6 同样可达。填写 `AUTOPPT_DOMAIN`，只填域名 |
| 网络与 HTTPS | 对外开放 80/443；Caddy 自动签发证书。不要映射 app 的 4318 端口。若现有代理占用 80/443，请由技术接入现有 HTTPS 代理，勿停止其他业务 |
| 管理员 | `AUTOPPT_ADMIN_USER`；密码写 `deploy/secrets/admin_password`，12–128 字符 |
| 内容理解模型 | `AUTOPPT_TEXT_BASE_URL`、`AUTOPPT_TEXT_MODEL`；Key 写 `deploy/secrets/text_key` |
| 图片生成模型 | `AUTOPPT_IMAGE_BASE_URL`、`AUTOPPT_IMAGE_MODEL`；Key 写 `deploy/secrets/image_key` |
| 配额与预算 | `AUTOPPT_SIGNUP_IMAGE_CREDITS=20`、并发 2、全站每日 2000 次/每人每日 300 次为起始值；设置供应商端预算告警，图片张数不等于真实账单 |
| 数据备份 | 独立受控备份位置，另存一份到其他磁盘或主机；建议保留最近 7 个每日备份与 4 个每周备份，由运维安排维护窗口，不在用户生成中停服 |

第一版接口要求：内容服务兼容 Chat Completions，支持图片输入并返回所需 JSON；图片服务兼容 Images Generations，内容附件需要 Images Edits 的多图支持，返回可读取的图片/base64，横向 16:9。基础地址通常含 `/v1`，不要填写具体 `/chat/completions` 或 `/images/generations` 路径。默认模型名称只是配置样例，请替换为实际可用模型，不保证任意供应商支持。

## 二、首次部署

以下从解压后的 `AutoPPT-Web/` 根目录执行。项目名统一使用 `autoppt-web`，升级时保持不变，避免创建另一套空数据卷。**如果已有线上部署，先确认原 Compose 项目名与数据卷，沿用原值，不要照抄新项目名。**

1. 校验收到的 ZIP，再解压到独立发布目录。例如 Linux：

```sh
sha256sum -c AutoPPT-Web-发布号.zip.sha256
unzip AutoPPT-Web-发布号.zip
cd AutoPPT-Web
cp deploy/release.env.example deploy/.env
mkdir -p deploy/secrets
chmod 700 deploy/secrets
```

2. 用编辑器填写 `.env` 和三个 secret 文件。`.env` 只放地址、模型名称、配额、版本等；不要放 Key。文件内容不加引号，不在命令行参数中传密码。Compose 文件型 secret 会保留宿主文件的读取权限；容器中的 UID 1000 必须能读取三个文件，可用 `chmod 444 deploy/secrets/admin_password deploy/secrets/text_key deploy/secrets/image_key`，由父目录 700 保护宿主机访问。Key 的备份应另行安全保存。

3. 检查配置；此步骤不请求模型，不创建账号：

```sh
docker run --rm -v "$PWD:/check:ro" -w /check node:24-bookworm-slim node deploy/check.mjs
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml config --quiet
```

4. 构建并启动：

```sh
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml build app
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml run --rm --no-deps app node -e "for (const n of ['admin_password','text_key','image_key']) require('fs').readFileSync('/run/secrets/'+n); console.log('容器可读取配置文件')"
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml ps
```

5. 打开 `https://你的域名/`，用管理员账号登录。在“使用帮助 → 版本与工作区”核对前后端提交号一致、运行形态为 hosted。在“账号设置 → 内部使用管理”创建一次性邀请码，交给测试同事。初始密码文件仅在首次创建管理员时使用，重启不会覆盖已修改的密码。

公网 `/api/health` 返回健康状态，不泄漏配置。日志可用 `docker compose ... logs --tail=100 app web` 查看；共享日志前检查是否含个人内容，不公开 secret 文件。网关后台端口不向宿主机映射，`/internal/` 在 Caddy 拦截。

## 三、正式开放邀请前验收

自动化验证使用模拟模型，**技术同事部署后仍需用自己的真实服务验收**；首次真实单页、重画和风格试做会产生供应商费用。

- 创建两个受邀账号。每个账号只看到自己的项目、风格、图片、历史与下载；直接打开另一个账号的项目和素材地址应失败。
- 新账号额度符合当前配置。先提交一小段文字生成一页，检查图片是否正确，保存图片、导出 PPTX/Markdown、修改并重画；每张成功图片扣 1 张。风格试做同样计入。
- 进入演练中心，普通放映、翻页、查看讲稿、退出正常；不会调用语音/数字人/动态制作服务。
- 在 App 导出一个测试项目包，网页版导入得到独立新项目。原 App 项目保留；导出的云端项目包可再次导入。已有口播、动态素材随包保留，第一版界面不制作这些内容；完整数字人视频和配置暂不包含在项目迁移包。
- 等待任务结束后正常重启，确认账号、项目、素材、历史、额度仍在；不自动重新发出收费请求。结果不明的生成由管理员先核对供应商记录，再释放预留额度。
- 完成下述备份、恢复到空卷的演练，再逐步发放更多邀请。没有验证真实模型效果、账单和服务承载前，不扩大到公开注册。

## 四、更新与回滚

持久化内容在 `autoppt_data` 卷中：账号数据库、每人工作区、图片/附件、历史、草稿与迁移进来的音频。Caddy 证书单独保存在 `caddy_data`。**禁止执行 `docker compose down -v`、删除数据卷或用本机 `.local/` 覆盖线上数据。**

更新前让使用者停止提交，逐个确认个人工作区的任务已结束；任务完成后正常停止 `app`，先备份。不要中断正在生成的任务。新发布包解压到新目录，将旧 `.env` 和秘密文件安全复制过去；更新其中的准确 `AUTOPPT_BUILD_GIT_SHA`/`AUTOPPT_BUILD_TIME`，其他配置保持，Compose 项目名保持一致。

在新目录完成配置检查、构建，再 `up -d`。登录检查版本、项目、素材、导出与余额，确认后留存发布记录。

回滚代码时，回到保留的旧发布目录，沿用相同项目名和数据卷，在任务结束后重新构建旧镜像并启动。第一版本次变化不重写现有数据。将来出现数据库结构升级时，应先确认向后兼容；若需回滚数据，按下面流程恢复至新空卷，原卷保留，核对备份时间后的新数据影响后再切换。

## 五、完整备份与恢复

随包提供 `scripts/hosted-backup.mjs`，使用流式 tar 压缩，避免将整个工作区加载进内存。备份附带 SHA-256 JSON 记录，保留二者。工具拒绝覆盖已有备份、拒绝恢复到非空目录，并检查账号/工作区 SQLite 完整性；只用于本工具制作的可信备份，不处理陌生压缩包。

首先等待用户任务结束，正常停止 app。取得该容器实际使用的数据卷名与镜像（不要猜卷名）：

```sh
APP_CONTAINER=$(docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml ps -q app)
DATA_VOLUME=$(docker inspect "$APP_CONTAINER" --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}')
APP_IMAGE=$(docker inspect "$APP_CONTAINER" --format '{{.Image}}')
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml stop app
mkdir -p /srv/autoppt-backups
chmod 700 /srv/autoppt-backups
BACKUP_NAME="autoppt-$(date -u +%Y%m%dT%H%M%SZ).tar.gz"
docker run --rm --user root -v "$DATA_VOLUME:/data:ro" -v /srv/autoppt-backups:/backup "$APP_IMAGE" node scripts/hosted-backup.mjs backup /data "/backup/$BACKUP_NAME"
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml start app
```

检查产生的 `.tar.gz` 与 `.tar.gz.json` 均存在，再另存到受控位置。不得只复制单个 SQLite 文件并遗漏 WAL、素材或账号数据库。定期备份的维护窗口、保存数量与异地存储由技术团队配置，本包不自动停止用户任务或删除旧备份。

恢复演练或故障恢复必须使用新的空卷；先保存并记录原卷名。替换下面的卷名和实际备份文件名：

```sh
RESTORE_VOLUME=autoppt-restore-20261010
docker volume create "$RESTORE_VOLUME"
docker run --rm --user root -v "$RESTORE_VOLUME:/data" -v /srv/autoppt-backups:/backup:ro "$APP_IMAGE" node scripts/hosted-backup.mjs restore /data /backup/实际备份.tar.gz
```

工具校验 SHA、压缩路径、文件类型与数据库数量，并将文件交还容器 UID 1000。恢复失败时保留空卷/恢复卷用于排查，勿覆盖原卷；重新尝试使用另一个空卷。

确认切换时，创建 `deploy/restore-volume.yaml`：

```yaml
volumes:
  autoppt_data:
    external: true
    name: autoppt-restore-20261010
```

在任务结束后停止 app，再从恢复卷启动：

```sh
docker compose -p autoppt-web --env-file deploy/.env -f deploy/compose.yaml -f deploy/restore-volume.yaml up -d app
```

登录核对账号、两个账号项目、素材、历史、导出和额度后，再对外开放。原数据卷继续保留。使用恢复卷后，所有后续维护命令都需加上这个 override 文件，避免误切回旧卷。管理员忘记密码的离线恢复工具和配置细节见 [线上部署说明](线上部署.md)。

## 六、交付验证边界

本次交付已完成以下隔离验证，未调用收费模型：

- Chrome 桌面/手机视口的邀请登录、个人工作区、账号管理和普通放映；翻页、讲稿、退出及键盘操作正常，放映不发送语音、数字人、动态或模型请求。
- 模拟服务下的两账号访问隔离、额度预留/扣减/失败核对，以及 HTTP 项目包导入导出；包内已有讲稿、素材和历史保留，原项目不被覆盖。
- Linux ARM64 原生与 AMD64 Docker 模拟环境、Node 24 容器以 UID 1000 运行；账号和项目经正常/异常重启保持，停止后从只读数据卷完整备份、校验并恢复到新空卷，恢复后原登录、项目与额度可用。
- 部署配置检查、Caddy 配置校验，以及部署 ZIP 的版本清单、文件 SHA 与不包含本机数据/秘密文件的检查。

生产域名/证书、真实模型账户、供应商账单、实际服务器架构与多人负载需技术团队上线验证；AMD64 模拟验证不代表真实服务器压测。容器不内置 Chrome；复杂动态网页风格导入可能失败，可使用上传参考图或手动风格规则。

现有 Mac App、本机 `~/Library/Application Support/AutoPPT/` 和仓库 `.local/` 均不在部署包内，部署不会自动连接、修改或清理这些内容。
