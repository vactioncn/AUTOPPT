# 从 Mac 增量发布到现有 Linux 服务器

入口：`bash scripts/deploy-server.sh`。默认目标为 `root@8.154.36.165:/opt/AutoPPT-Web`，公网地址为 `https://aippt.pinguo.cn`，Compose 项目名为 `autoppt-web`。脚本兼容 macOS 自带 Bash 3.2 和 rsync，不在 M1 上构建 Linux 镜像；构建发生在服务器上。

## 以后给 Codex 的提示词

> 请验证并提交当前已完成代码，再执行 `bash scripts/deploy-server.sh --dry-run` 和 `bash scripts/deploy-server.sh`，将最新版本发布到服务器。执行期间跟进输出；只有脚本退出码为 0 且输出“发版成功”后才向我报告成功，并给出发布编号和访问地址；失败时排查实际错误，不要删除数据卷或覆盖服务器的 .env、Key。

这是普通按需发布脚本，没有创建定时任务，也不会在编辑代码后自行发布。首次可以先执行：

```bash
bash scripts/deploy-server.sh --dry-run
```

预演只读取服务器部署信息并输出 rsync 变更列表，不同步、不重启、不申请证书。首次 SSH 主机指纹应已由维护者确认；脚本使用 BatchMode，不会自动接受未知主机指纹或交互输入密码。

## 发布过程

1. 校验脚本所在目录就是 Git 仓库根目录，拒绝从嵌套旧发行目录发布；存在已跟踪文件的未提交改动时拒绝发布。通过 `git archive HEAD` 创建已提交代码快照，未跟踪的旧程序、私密资料和临时文件不会进入上传范围；构建 SHA 对应确切代码，另记录 UTC 构建时间及唯一发布编号。预演和正式发布采用同样的快照方式。
2. 从正在运行的应用容器读取原 Compose 文件列表、working directory、数据卷与正式地址。沿用原配置，只更新 app 服务，避免重新启动 Caddy。服务器必须已有一个运行中的 `autoppt-web/app` 容器，且 `deploy/.env` 已配置。
3. 在 `.deploy/` 中加锁、保存旧镜像标签、源码快照及受限访问的配置快照。用 rsync 增量同步代码，并删除本地已删除的旧源码。排除规则保护服务器专属内容，见 `deploy/rsync.exclude`。
4. 先检查合并后的 Compose 数据卷与正式地址，再构建新镜像。构建失败不会停止旧容器。检查已有任务；发现排队/运行中的持久化任务就退出，等待任务完成后再发布。请在维护窗口执行并暂停提交新任务；任务检查与停止之间仍有短暂间隙，脚本没有实现全站请求排空。
5. 正常停止 app，通过旧镜像中的 `hosted-backup.mjs` 完整备份原数据卷，再更新 app。此阶段会有短暂停机。构建时传入本次 SHA/时间，不修改服务器 `.env` 的模型和密钥配置。
6. 验证新容器仍挂载原数据卷、Docker 健康检查通过、镜像前后端构建清单匹配。再从服务器和 Mac 分别请求公网健康接口及构建清单；公网 SHA/构建时间必须与本次发布一致，才输出“发版成功”。这些检查不调用收费模型，也不等于真实模型生成验收。

## 保留与备份

不会上传或删除 `.env` / `.env.*`、`secrets/`、`.local/`、`.hosted/`、`music/`、`node_modules/`、本地构建产物、Git/Codex 元数据、旧 TokenHub 补丁 ZIP、旧发行压缩包和 `AutoPPTweb-codex/`。服务器现有的 `deploy/fonts/*.fntdata` 与字体清单保留，不用缺少二进制字体的 Git 源码覆盖它们。Docker 数据卷不在 rsync 范围内，不执行 `down -v`。Nginx / 宝塔配置不在项目目标目录中，脚本不会修改它们。

`deploy/compose.nginx.yaml` 只启动应用，将内部 4318 映射到服务器回环地址 14318，沿用宿主机 Nginx 的 HTTPS；构建默认使用同事配置的 `mirror.camera360.com/base/node:24-bookworm-slim`，可通过服务器 `.env` 的 `AUTOPPT_NODE_IMAGE` 调整。普通 `compose.yaml` 部署仍默认使用官方 Node 镜像。当前正式发布固定整图生成，保留混元模型接口适配；语音等功能沿用服务器已有配置，不在升级时自动启用。

每次发布保留：

```text
/opt/AutoPPT-Web/.deploy/releases/<发布编号>/
  source-before/          旧源码快照（硬链接；后续 rsync 通过替换文件更新）
  config-before/          原 Compose 文件及 .env
  data.tar.gz             正常停服后的完整用户数据备份
  data.tar.gz.json        备份校验记录
  success                 完成全部验收后才写入

旧镜像标签：autoppt-web:before-<发布编号>
最后成功记录：/opt/AutoPPT-Web/.deploy/last-success
```

备份不会自动清理，需按磁盘容量设置保留策略并异地备份；配置及用户备份包含敏感数据，目录默认仅维护者访问。构建前失败的发布不会产生数据备份，因为应用尚未停止。

失败时返回非零退出码，不会伪报成功。若备份失败且旧容器仍存在，会尝试重新启动旧容器。新容器启动或验收失败时保留现状与备份，不自动恢复数据库或回滚代码，避免新旧数据格式不兼容时进一步损坏。应先查看实际错误，再选择旧镜像/源码修复。

若发布进程或 SSH 被强制中断，可能留下 `.deploy/lock`。先确认服务器无发布、构建、备份进程在运行，再手动清除该锁目录；不要直接删除整个 `.deploy`。未使用本脚本的人工发布不受该锁约束。

## 可选覆盖

```bash
AUTOPPT_DEPLOY_HOST=root@其他主机 \
AUTOPPT_DEPLOY_ROOT=/opt/AutoPPT-Web \
AUTOPPT_COMPOSE_PROJECT=autoppt-web \
AUTOPPT_DEPLOY_URL=https://aippt.pinguo.cn \
bash scripts/deploy-server.sh
```

路径必须为无空格的绝对路径；本地项目路径可包含空格或中文。服务器需要 Bash、rsync、curl、Docker 与 Compose 插件；Mac 需要 Bash、rsync、SSH、curl、Git 与系统 base64。服务器不需要宿主机 Node，JSON/版本/任务校验使用现有应用容器的 Node。

如果服务器原 Compose 文件不在 `/opt/AutoPPT-Web` 内、数据使用 bind mount、包含多个 app 副本，或 `deploy/.env` 之外还有额外环境文件，本脚本不能直接代替该部署流程，应先调整脚本。首次正式发布前建议预演并核对它识别出的 Compose 文件。
